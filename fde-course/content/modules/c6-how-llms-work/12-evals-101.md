In customer conversations it's the difference between "it seems better" and "it went from 86% to 94% on 200 of your real tickets". E4 goes deep; this lesson is the minimum every track needs. ## What an eval is

An eval is a fixed set of **cases** (inputs, plus what a good output looks like), a way to **run** your system on them, a **grader** per case, and a **report**. It's a regression test suite for behaviour that isn't deterministic.

Build the case set from reality: real user requests (with permission and redaction), known failure cases, edge cases, and cases where the right answer is "I don't know" or a refusal. Fifty good cases beat five hundred synthetic ones that don't look like production.

## Graders, cheapest first

| Grader | Use when | Watch out for |
|---|---|---|
| **Exact match** (after normalizing case and whitespace) | Labels, enums, IDs, short factual answers | Too strict for free text; normalize consistently |
| **Code checks** | JSON validity, schema, required fields, numbers within tolerance, a cited span exists, a SQL query runs | Only checks what you code |
| **LLM judge with a rubric** | Free text: helpfulness, tone, faithfulness to sources, following a policy | The judge is a model too: it has biases (length, position, self-preference) and variance |
| **Human review** | Calibrating the judge, high-stakes launches, new failure types | Slow and expensive; use it to check the automatic graders, not instead of them |

Rules for an LLM judge that holds up in an interview:

- **Grade against a written rubric**, one criterion at a time, and ask for a verdict in a fixed schema (for example `{"pass": true, "reason": "..."}` via structured outputs). Ask for the reason with the verdict so you can audit it.
- **Calibrate**: grade 30–50 cases by hand and check the judge agrees. Report the agreement rate.
- **Set effort deliberately** for the judge model (low is often enough for a narrow rubric), and keep the judge model and prompt fixed while you compare systems.
- **Prefer binary or small scales.** "Pass or fail on this criterion" is more stable than a 1–10 score.

## Run it more than once

The system under test samples, so one run per case hides flakiness. Run each case N times (3 to 5 is common for a quick check) and report:

- **Pass rate over all trials**: passes ÷ (cases × N).
- **Per-case consistency**: which cases pass sometimes and fail sometimes. Those flaky cases are where your prompt is ambiguous.
- Where it matters, stricter summaries such as "passed all N runs".

## Confidence intervals: is 92% better than 88%?

A pass rate from a sample is an estimate. Report an interval. The **Wilson score interval** behaves well even near 0% or 100%, unlike the simple "p ± 1.96·√(p(1−p)/n)":

```text
p = k / n,  z = 1.96 for 95%
centre = (p + z²/(2n)) / (1 + z²/n)
half   = z · √( p(1−p)/n + z²/(4n²) ) / (1 + z²/n)
interval = [centre − half, centre + half]
```

| Result | 95% Wilson interval |
|---|---|
| 46 / 50 (92%) | 81.2% to 96.8% |
| 44 / 50 (88%) | 76.2% to 94.4% |
| 184 / 200 (92%) | 87.4% to 95.0% |
| 10 / 10 (100%) | 72.2% to 100% |

The first two overlap heavily: on 50 cases you can't claim the 92% prompt is better. The last row is the one to remember: ten out of ten is not "100% accurate". Overlapping intervals are a rough check, not a formal test; for a careful comparison run both systems on the same cases and look at the cases where they differ. One more caveat to say out loud: N runs of the same case aren't independent samples of new cases, so more runs tighten the estimate of *this* case set, not of production. More diverse cases do that.

## A model answer

"How would you know the new prompt is better?"

"I'd run both prompts on the same 200 real cases, three runs each. Labels are graded by exact match, free-text answers by a rubric judge that I've checked against 40 hand-graded cases. I'd report the pass rate with a 95% Wilson interval for each, list the cases that flipped between them, and look at the flaky ones. If the intervals overlap a lot, I'd say we can't tell yet and add cases, especially from the categories that changed. I'd also keep the cost per case and latency in the same table, because a better prompt that doubles cost may not win."

> **Key takeaways**
>
> - An eval is cases, a runner, graders and a report. Build cases from real traffic, including "I don't know" cases.
> - Use the cheapest grader that works: exact match and code checks first, a calibrated rubric judge for free text, humans to check the judges.
> - Run cases several times, report the pass rate and the flaky cases.
> - Report a Wilson interval. Small samples can't separate close results: 10 out of 10 is not 100%.
